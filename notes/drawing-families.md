# 寸法図からCADへ：複数穴・確認操作・部品形状の拡張

2026-10-22。独立した探索研究。リリース番号・v1.15〜v1.24の業務計画は変更しない。

[結果HTML](../results/drawing-families/report.html) /
[再現・操作手順](../docs/drawing-families.md) /
[全観測](../results/drawing-families/results.json)

## Research Question

明示した部品種別と三面図の対応を前提に、実CADが出力する通常の寸法を根拠として、
複数穴付き板・L字・段付き軸・矩形ポケットまで編集可能なCADを復元できるか。
不足する寸法を図形の縮尺から埋めず、保留理由と確認対象を提示できるか。

最終ゴールの「任意の機械図面からの自動復元」の達成は主張しない。
今回のゴールは、限定した4ファミリーで入力→根拠→CAD→独立正解との照合→編集をつなぐこと。

## Source Review / 既存資産の再利用

- [前回のSVG/DXF一致検証](cad-svg-dxf.md)の正規化、寸法線と矢印の幾何照合、固定FreeCAD実行環境を再利用。
- 既存のプレート用パラメトリックフィーチャー、OCPプリミティブ・Boolean、STEP出力・再読込、
  B-Rep検証・体積差分・HLR投影・実形状のテッセレーションを再利用。
- HTMLの回転可能な3D表示は既存のオフライン表示を再利用。新しいCADカーネル・AIモデルは導入しない。
- [FreeCAD 1.1.4の寸法実装](https://github.com/FreeCAD/FreeCAD/blob/1.1.4/src/Mod/TechDraw/App/DrawViewDimension.cpp)
  を参照し、TechDrawの頂点・稜線参照から通常の寸法オブジェクトを作る。
- [W3CのSVG円弧変換](https://www.w3.org/TR/SVG11/implnote.html#ArcImplementationNotes)
  と [tspanの仕様](https://www.w3.org/TR/SVG11/text.html#TSpanElement) を参照。
  SVG仕様全体への対応ではなく、円弧と単純な文字ランに絞る。

資料参照、実装、実測を区別する。別CADの出力や任意のSVG仕様の動作は確認していない。

## Method Selection / 実施範囲

| 前回提示した段階 | 今回の実施内容 | 残る範囲 |
|---|---|---|
| 1. 未知の図面設定 | 新しい縮尺・文字サイズ2条件を、変更前コードで先に判定し保存 | 別CADは未実施。適応後は開発データ |
| 2. 寸法表記 | 共有位置寸法、2 × 径6の数量表記、文字位置ずれ、同一親内の分割寸法線 | 公差、一般的な連鎖寸法、半径、任意の引出線は未対応 |
| 3. SVG構文 | 円弧A、直線相当のQ、単純なtspan。文字アウトラインの負例 | 楕円、任意曲線、位置指定付きtspan、アウトライン文字認識 |
| 4. 複数穴 | 異径2穴・共有Xの3穴・数量注記を照合 | 4穴以上、重なり、任意の穴群指定 |
| 5. 人の確認 | 寸法端点の強調、根拠ID、保留理由、ビューと投影法のJSON保存→CLI再計算 | ブラウザー内のCAD再計算・寸法修正・一般的なビュー検出 |
| 6. 部品形状 | L字、2段の同軸円柱、単一の閉じた矩形ポケット | 複合形状、複数ポケット、L字への穴追加、フィレットなど |

非AIのベクター解析（方式C）を継続。図面から寸法の根拠を保持する中間モデルを作り、OCCTで生成する。
部品ファミリーは人が指定する。ファミリー分類器・VLM方式・OCR方式の比較は行っていない。

## Controlled Experiment / 入力と独立正解

FreeCAD 1.1.4 / OCCT 7.8.1で自作した11ページをSVG/DXFへそのまま出力。
A3、mm、第三角法、正面・平面・右側面を用いる。
正解と編集後正解は、FreeCAD側のPart操作で別々に生成したSTEPと設計値を評価側へ保存した。
再構成側はcadquery-ocp 7.9.3.1.1を使う。両者ともOCCT系列であり、独立カーネルではない。

| 入力群 | 実CADページ数 | 入力ファイル数 | 期待 |
|---|---:|---:|---|
| 新しい縮尺0.85/文字2.5 mm、縮尺1.2/文字4.2 mm | 2 | 4 | 復元 |
| 異径2穴、X共有3穴、数量2穴 | 3 | 6 | 復元 |
| L字、段付き軸、矩形ポケット | 3 | 6 | 復元 |
| 壁厚なし、小径なし、深さなし | 3 | 6 | 保留 |
| 元SVGから派生した構文・表記の正例 | — | 5 | 復元 |
| アウトライン文字、位置指定tspan、数量矛盾、投影法不明、ビュー誤指定 | — | 5 | 保留 |
| 合計 | 11 | 32 | 正例21 / 負例11 |

32入力を各2回、64試行。反復は独立した部品数ではない。
派生10入力は実CAD出力の原本ではなく、同じ2部品の表記対照。
アウトライン文字はDejaVu Sansへ置き換えた実際の文字輪郭で、元FreeCADフォントの完全再現ではない。
[出所・ライセンス](../fixtures/drawing-families/README.md)を参照。

人が与えるもの:
- 単位mm、投影法、4種類のいずれかの部品種別。
- SVGの図面グループと3つの代表パス、またはDXFの3レイヤーの役割。
- 原本の選択スクリプトは3フレームを列挙し、作図順との対応を人が確認する。自動ビュー認識ではない。

プログラムが取得するもの:
- 図形、XML文字またはDXF寸法、対応する形状上の端点、穴径・数量・貫通指示。
- 寸法から定まる外形・穴位置・厚さ・段差・ポケット寸法。
- 図形と寸法の一致に使う縮尺。縮尺を使って欠けた設計寸法を補完しない。

復元CLIへ渡すのは入力1ファイルと非数値contextのみ。対になる形式、元FCStd、正解STEP、設計値は渡さない。
別名の入力を一時ディレクトリへコピーしたテストでも復元を確認した。
通常の子プロセス分離であり、OSアクセス権で正解へのアクセスを禁止するサンドボックスではない。
コードが正解を読まないことと入力境界を検査している。

## Evaluation / 観測

変更前のコードはコミットc95aecaのまま保持し、SHA-256を保存した。
未観測だった2設定・4入力の初回判定は3件candidate、1件svg_path保留。
保留の原因はSVGの径引出線が接続した2サブパスになることだった。
これは「候補生成の初回判定」であり、旧処理の全工程成功率ではない。
以降はこのデータを見て適応したため、最終結果をホールドアウト精度とは呼ばない。

| 検査 | 固定結果 |
|---|---|
| 正例21入力（42試行） | CADコード実行・単一ソリッド・STEP再読込・寸法・形状・編集を通過 |
| 負例11入力（22試行） | 期待した理由コードと一致して保留 |
| 負例の誤確定 | 0 / 11入力 |
| SVG/DXFの正例8組 | 抽出パラメータが一致。復元・編集後とも体積IoU 1.0 |
| SVG/DXFの負例3組 | 両形式でdimension_missing |
| 抽出パラメータ最大誤差 | 0 mm |
| 復元・編集後STEPの外形最大誤差 | 0 mm |
| 復元・編集後STEPと解析式の体積差最大 | 約4.002 × 10^-11 mm³ |
| 表面積差最大 | 約1.292 × 10^-10 mm² |
| HLRと入力のサンプル最大残差 | 約0.00447243 mm |

形状一致は評価側でBooleanによる対称差体積からIoUを計算する。
公称寸法の一致、体積・面積の解析式、境界寸法、全体体積IoUを組み合わせる。
穴などの位置をパラメータ比較だけで成功扱いにせず、生成後の形状全体も照合する。
ただし全形状の位相・面ごとの意味が同一であることや、元作者の履歴の復元は保証しない。

解析式:
- L字: 断面積A = 奥行×底板厚 + 壁厚×(高さ−底板厚)、体積=幅×A、
  表面積=2A + 2幅(奥行+高さ)。
- 同軸2段軸: 体積=π(r1²l1+r2²l2)、表面積=2π(r1l1+r2l2+r1²)。r1>r2。
- 閉じた矩形ポケット: 直方体体積−ポケット幅×奥行×深さ。
  表面積は元直方体面積 + 2深さ×(ポケット幅+奥行)。
- 穴付き板は矩形板から円柱体積を除き、円柱側面を加え、両端の円面を除く。

許容値は抽出寸法・外形1e-6 mm、体積1e-5 mm³、面積1e-5 mm²、IoU>=1−1e-8。
図面上の幾何照合EPS=0.002 mm、再投影サンプル残差<=0.02 mm。
円弧をベジェ化した描画誤差とOCCT投影のサンプリング誤差を含む。厳密なHausdorff上界ではない。

編集は全正例で別スクリプトを実行:
- 板: 幅+5、厚さ+2、左端の穴Xと径+1 mm。
- L字: 幅+5、高さ+3、底板厚+1 mm。
- 軸: 大径部長さ+4、小径+1 mm。
- ポケット: 板幅+5、ポケット幅+2、深さ+1 mm。

FreeCAD側で作った編集後正解とも照合する。保存Python/JSONは編集可能な再生成レシピで、元の設計履歴ではない。

## 人の確認・失敗の扱い

- 壁厚、小径、ポケット深さが欠けるとdimension_missing。断面の見た目から値を入れない。
- 数量と同径円の個数が矛盾するとquantity_conflict。
- 文字がパスのみならtext_unavailable、位置付きtspanはsvg_text_layout。
- 投影法不明はprojection_unknown、今回の正面/平面取り違えはdimension_conflict。
- パーサーの例外はdrawing_parse_failure、カーネル例外はkernel_failure。
  実行・評価側の例外もCAD生成、編集生成、評価段階を別に残す。
- 異なる壁厚のCADを生成させる対照テストではreprojection_conflictとなる。

HTMLは寸法値→参照端点→パラメータを表示する。
ビュー指定の重複ではJSON保存を無効化し、変更後は「条件変更・未再計算」と明示する。
実ブラウザーで正面/平面の誤指定を修正してJSONをダウンロードし、
そのJSONをCLIへ渡して保留→candidate→STEP出力を確認した。
[保存した修正条件](../results/drawing-families/review-correction/context.json)と
[再生成結果](../results/drawing-families/review-correction/regenerated/inference.json)を残す。
これはエージェントによる操作検証で、利用者の作業時間・使いやすさの実験ではない。

## Limitations / 成立条件

全テストは1,528件通過（373.43秒）。今回追加した69件には32固定入力、入力隔離、
欠落・矛盾、数量、共有寸法、無効パラメータ、描画単位、意図的なカーネル失敗と再投影不一致を含む。
ブラウザーでL字・軸・ポケット、寸法根拠、保留、条件JSON保存とCLI連携を確認した。

1. FreeCADの自作図面だけ。別CAD、顧客図面、未知ファミリー、Windowsネイティブ実行は未確認。
2. 部品種別・ビューの役割は人が指定。線種の意味、可視/隠れの区別を合否に用いない。
   投影線集合が同じでも、ポケットの向きや内部形状に別解が存在し得る。指定ファミリー内の候補である。
3. L字は穴なし・直交・一定厚、軸は同軸の2段、ポケットは上面から1個の閉じた矩形。
   フィレット・面取り・ねじ・アセンブリ・自由曲面は対象外。
4. 穴は3個までの分離したZ方向丸貫通穴、明示THRUが必要。数量は同径の円群全体へだけ適用。
5. 円弧Aは正の円半径・通常フラグ・半径補正不要に限定。任意曲線のCAD復元ではない。
   Qは変換できても、図形解釈が受け付けるのは直線相当だけ。tspanは位置・書式指定なしだけ。
6. 公差・はめあい・GD&T・切断面・任意の寸法チェーン・画像OCR・AIは未対応。
7. 入力上限・子プロセスタイムアウトは一般的な悪意あるCADの安全性保証ではない。
8. 上の小さな開発群の合格は、業務の自動化率・ROI・新規性の証明ではない。

## 次の優先順位

| 順番 | 研究 | 判定したいこと |
|---:|---|---|
| 1 | 別CADの同一部品・別設定を変更前コードで評価 | CAD依存の表記と、幾何解析の不足を分けられるか |
| 2 | 可視線/隠れ線と断面図 | 同じ投影輪郭でも異なる内部・向きを誤確定しないか |
| 3 | 新しい寸法を持つ各ファミリーの未観測部品 | 開発例だけで通る処理になっていないか |
| 4 | 寸法公差・数量・連鎖寸法の中間表現 | 公称値と許容差、派生値の根拠を保存できるか |
| 5 | L字＋穴などの複合フィーチャー | 一致した体積だけでなく編集対象を正しく追跡できるか |
| 6 | PNG/PDFへの限定OCRまたはVLMの比較 | 非AIベースラインより入力対応が増え、誤確定を抑えられるか |

先に評価用入力と正解・保留条件を固定し、その後に実装する。
[検証記録](../results/drawing-families/verification.json)に実行テスト数・ハッシュ・未実施項目を保存する。
