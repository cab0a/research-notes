# AP242 Assembly Occurrences, Placements, and Units

## 日本語概要

## English Summary

This study distinguishes reusable AP242 product definitions from their placed
assembly occurrences. A controlled evaluator links immediate product
structure to context-dependent shape relationships, evaluates paired 3D
placements as child-to-parent rigid transforms, composes nested paths, and
normalizes supported length units to millimetres. Seventeen synthetic STEP
fixtures separate evaluated, deferred, invalid, and resource-bounded routes.

## Research Question

Can a source-preserving Part 21 graph support a defensible, testable assembly
interpretation that keeps component definition, occurrence identity,
transformation direction, nesting, and unit conversion distinct?

The controlled path is:

```text
NEXT_ASSEMBLY_USAGE_OCCURRENCE
  -> parent PRODUCT_DEFINITION
  -> child PRODUCT_DEFINITION
  <- occurrence PRODUCT_DEFINITION_SHAPE
  <- CONTEXT_DEPENDENT_SHAPE_REPRESENTATION
  -> REPRESENTATION_RELATIONSHIP_WITH_TRANSFORMATION
     rep_1 -> child SHAPE_REPRESENTATION
     rep_2 -> parent SHAPE_REPRESENTATION
     operator -> ITEM_DEFINED_TRANSFORMATION
                 item_1 -> child AXIS2_PLACEMENT_3D
                 item_2 -> parent AXIS2_PLACEMENT_3D
```

## Background

An assembly definition and an assembly occurrence are not interchangeable. A
product definition can be referenced by several immediate usage relationships,
each with its own reference designator and placement. Collapsing those links by
child definition would lose repeated components.

The public ISO 10303-41 material describes
`CONTEXT_DEPENDENT_SHAPE_REPRESENTATION` as the association between a product
definition relationship and a shape representation relationship. In that
relationship, `rep_1` corresponds to the related product definition, the
component, while `rep_2` corresponds to the relating product definition, the
assembly context. ISO 10303-43 describes an individual
`ITEM_DEFINED_TRANSFORMATION` as a transformation derived from two
representation items, commonly two `AXIS2_PLACEMENT_3D` instances in their
respective coordinate spaces.

For the controlled placement pair, let (F_c) be the homogeneous frame of
`transform_item_1` expressed in the child representation unit and (F_p) the
frame of `transform_item_2` expressed in the parent representation unit. After
normalizing both origins to millimetres, the implemented child-to-parent map is:

```text
M_child_to_parent = F_parent @ inverse(F_child)
M_child_to_root = M_parent_to_root @ M_child_to_parent
```

This order is a critical claim boundary. Reversing the frames can still produce
a finite, plausible-looking matrix, so transformation direction requires
independent controls rather than visual plausibility alone.

## Method

The evaluator reuses the source-preserving Part 21 parser and directed
multigraph. It admits one exact schema identifier,
`AP242_MANAGED_MODEL_BASED_3D_ENGINEERING_MIM_LF`, and applies a hand-selected
role map for the entity chain above.

For every `NEXT_ASSEMBLY_USAGE_OCCURRENCE`, it:

1. validates the required parent and child product definitions;
2. resolves one product-to-representation path for each definition;
3. joins the occurrence through its product-definition shape and
   context-dependent shape relationship;
4. requires `rep_1` to be the child representation and `rep_2` the parent;
5. requires an individual `ITEM_DEFINED_TRANSFORMATION` with explicit 3D
   placements present in the corresponding representation item aggregates;
6. evaluates each placement from a point, axis, and reference direction;
7. obtains one length unit from each distinct representation context;
8. recursively evaluates supported SI metre prefixes and conversion-based
   length units into millimetres;
9. evaluates the child-to-parent rigid transform and composes root-relative
   paths; and
10. retains every semantic role with the exact physical reference edge,
    parameter path, and source span that supports it.

Axis and reference directions must be finite, non-zero, and orthogonal in this
subset. A proper rotation determinant is checked after frame evaluation.
Reference designators must be unique within one parent definition. Occurrence,
path, relation, depth, and unit-conversion-hop budgets bound semantic work.

## Controlled Experiment

All inputs are generated by
[`ap242_assembly_study.py`](../src/research_notes/ap242_assembly_study.py). The
corpus contains 17 readable `.step` files and a deterministic hash manifest.
Every model uses synthetic products and block primitives.

| Group | Controlled condition | Expected handling |
| --- | --- | --- |
| Transform evaluation | translation, 90-degree rotation, non-origin source frame | accept |
| Structure and reuse | one subassembly and three occurrences of one reused part | accept |
| Unit conversion | inch child placement in a millimetre parent | accept |
| Optional path | no occurrence, missing occurrence shape, missing context-dependent relationship | quarantine |
| Subset and work boundary | unsupported operator, absent length unit, depth budget | quarantine |
| Semantic invalidity | reversed representation order, nonorthogonal axes, unresolved child, duplicate designator, assembly cycle, unit cycle | reject |

The controls isolate four easy-to-confuse calculations:

- A target origin of `(10, 20, 30)` millimetres verifies direct translation.
- A target x direction of `(0, 1, 0)` verifies a positive 90-degree z rotation.
- Child and parent frame origins of `5` and `20` millimetres verify a `15`
  millimetre child-to-parent translation, not the inverse or their sum.
- A rotated subassembly at `(100, 0, 0)` with its child at local `(10, 0, 0)`
  verifies a root-relative result of `(100, 10, 0)`.
- A child source origin at `1` inch and parent target origin at `50.8`
  millimetres verifies a normalized result of `25.4` millimetres.

Run the committed corpus with:

```bash
python experiments/run_ap242_assembly.py
```

Regenerate the STEP fixtures only when intentionally changing their
definitions:

```bash
python experiments/run_ap242_assembly.py \
  --fixture-dir fixtures/ap242-assemblies \
  --refresh-fixtures
```

## Interpretation

The result establishes three useful distinctions.

First, definition identity is not placement identity. Reuse is represented by
several occurrence records that point to one child definition; each occurrence
needs its own path and transform.

Second, a representation relationship is directional. The component is
`rep_1`, the parent context is `rep_2`, and the paired placement ordering must
be consistent with that relationship. A finite inverse matrix is not evidence
that the correct direction was chosen.

Third, coordinates have no safe common scale until their representation units
are interpreted. Normalizing frame origins before matrix composition prevents
an inch coordinate from being treated as a millimetre coordinate while still
retaining the original declaration and conversion chain.

The accepted result means only that this controlled semantic path was
evaluated. It does not mean that the complete AP242 schema, every assembly
encoding, or the represented B-rep is valid.

## Failure Modes

- Collapsing occurrences by child definition loses repeated placements.
- Swapping `rep_1` and `rep_2` produces the wrong direction even if all
  references resolve.
- Applying `F_child @ inverse(F_parent)` can produce a plausible inverse
  transform.
- Composing nested matrices in leaf-first order moves components to the wrong
  root-relative location.
- Treating every length coordinate as millimetres silently scales imported
  geometry incorrectly.
- A conversion-based unit can contain an invalid or cyclic conversion chain.
- Duplicate reference designators make occurrence-level reporting ambiguous
  within one parent.
- Product structure can contain a cycle even when each immediate reference is
  syntactically valid.
- A transformation select can name a function or a set of associations rather
  than the individual item-defined rigid transform evaluated here.
- An absent optional relationship and an invalid required relationship should
  not receive the same decision.

## Practical Guidance

- Preserve product definitions and occurrences as separate record types.
- Report a path as a sequence of reference designators, not only a leaf part
  identifier.
- State transformation direction in names, formulas, tests, and exported
  fields.
- Normalize length values to a declared canonical unit before composition and
  retain source-unit provenance.
- Test source-frame offsets and rotations; origin-only translations cannot
  expose every ordering error.
- Detect cycles and impose explicit traversal and conversion budgets before
  recursive evaluation.
- Keep semantic roles joined to physical Part 21 edges so a disputed result is
  traceable to exact source text.
- Do not hand an accepted path to geometry or manufacturing logic as proof of
  AP242 conformance.

## Limitations

- The evaluator is not a complete implementation of ISO 10303-242.
- Only one exact AP242 MIM schema identifier and one controlled occurrence
  encoding are admitted.
- The role map is hand-selected rather than generated from the complete AP242
  EXPRESS schema and conformance classes.
- Only individual `ITEM_DEFINED_TRANSFORMATION` values with explicit
  `AXIS2_PLACEMENT_3D` items are evaluated.
- Functionally defined transformations, transformation sets, mapped items,
  kinematic joints, mirroring, scaling, and non-rigid transformations are not
  evaluated.
- Missing placement axis or reference direction is deferred instead of using
  schema-defined defaults.
- Supported units are SI metre prefixes and recursively conversion-based
  length units. Derived units, context-dependent units, uncertainties, and
  complete dimensional-exponent validation are not implemented.
- The synthetic corpus is small and does not establish behavior across CAD
  exporters or application-protocol editions.
- Block geometry is present for visual inspection, but geometry is not moved,
  tessellated, rendered, intersected, or checked for collision.
- B-rep topology, tolerance, face geometry, mass properties, and manufacturing
  validity are outside this study.
- `accept` means the controlled path and transform were evaluated, not that the
  file is conformant, interoperable, safe, or suitable for production.

## Questions Carried Forward

1. Which geometry kernel and Python binding provide the required B-rep access,
   deterministic headless evaluation, packaging, and acceptable licensing
   boundary?
2. How should analytical truth for face area, centroid, UV bounds, normal, and
   tolerance be constructed independently of the selected kernel?
3. Which additional AP242 assembly forms must be supported before real
   exporter samples can be compared without overgeneralizing from one mapping?
4. How should assembly placements be attached to evaluated solids while
   retaining both source-level and kernel-level provenance?
5. Which validation stage should decide whether a semantically resolved but
   geometrically invalid component remains inspectable or must be quarantined?

The first two questions define the next studies: a geometry-kernel and license
decision followed by evaluated face geometry and tolerances.
